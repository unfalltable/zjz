# MIOVA 妙物

面向海外消费者的跨境购物项目。按已确认的方案：Web 商城保留 React / Vinext，App 使用 Flutter，服务端代码与管理页面统一放在 `backend/`，共用商品与订单逻辑。支付暂缓，不收款、不假装支付成功。

## 账号模块替换整合（2026-10-27）

以提供的《完整版账号登录模块》为功能基准，账号服务统一到 `backend/api/account/`；旧 `user_account/` 入口只转发同一实现，不再运行两套账号逻辑。商城新增 `/account`，接入邮箱／手机号登录、注册、重置密码和个人资料；浏览器会话使用 HttpOnly Cookie。验证码、邮件／短信及第三方登录按真实配置开放，缺少配置时明确提示不可用。

本次没有修改真实账号数据、自动执行数据库迁移或切换线上服务。新库 SQL、现有库只读结构检查、部署配置、接口兼容和验证范围见 [账号整合说明](docs/account-integration.md)。Flutter 登录界面及原生第三方登录 SDK 尚未接入；支付仍关闭，管理后台认证保持独立。

## 配送报价确认（2026-10-15）

Web 结算使用公开只读配送接口，按实际 SKU、数量、服务端价格和重量计算报价，不采信客户端传入的价格或包裹重量。无可用路线、暂时失败或请求超时时阻止继续，可重试；切换目的地会取消旧请求。支付继续关闭，保存的需求不扣款、不预占库存、不安排发货。

用户在配送步骤点击“核对需求”时保存已确认报价。商品价格、运费、时效或可用服务发生变化，必须回到配送步骤重新核对；目录刷新与自动选择可用服务不能替代用户确认。服务端再次核对金额与配送版本，防止确认后到保存前的变化。地址和邮箱保留在当前页面内存中。

同一幂等键的并发请求在缺货、涨价或配送校验拒绝前，会再次核实是否已有等价请求被接受；已接受时回放原订单快照，异内容仍返回 409。新增交错时序测试覆盖上述并发情况。

生产配送验收入口：`npm run test:selfhost-shipping`，也已加入 `npm run test:selfhost-build`。它启动真实 Node Web 生产包并使用独立临时数据库与媒体目录，覆盖 SKU 报价、价格／重量防篡改、配置脱敏、旧报价拒单、零运费、同键回放与库存不变。修改后需先运行 `npm run build:selfhost`。

本轮还使用隔离 Chrome 验证商品涨价与路线停用同时发生、提交期间路线变化、无路线与网络失败重试，以及响应丢失后按原请求恢复。手机宽度 390px 下无横向溢出。当前页面内恢复可保留原请求；刷新页面后无法重建完全相同请求的安全恢复机制仍待实现，不能承诺跨刷新自动去重。发布与线上验收状态以对应提交的发布记录为准。

## 商品规格搜索（2026-10-14）

目录接口现在可通过子规格 SKU 和规格名称／值找到所属商品组，例如 `CUP-RED-LARGE` 或 `Color: Red`。空白分隔的多个关键词必须全部匹配，可跨公开商品字段；返回完整商品组与全部有效上架规格，方便切换选项。仅匹配公开展示资料，不搜索子规格内部名称、下架／无效规格或其他店铺数据。

服务端与 Web 共用 NFKC、空白和大小写处理，支持全角文字与组合重音；SQL 通配符按字面处理。游标继续绑定店铺、规范化搜索、分类、语言和排序，搜索与无搜索分页均不写入业务数据。规格查询按最多 99 个主商品分批，加店铺参数后不超过 D1 的 100 个绑定参数限制。

回归验证入口为 `npm run test:commerce`、`npm run test:d1` 和构建后的 `npm run test:selfhost-build`。测试使用隔离数据库，覆盖子规格命中、店铺隔离、下架／无效规格、稀疏匹配分页、Unicode 以及真实 Node 生产接口。

当前仍使用批次扫描与文字匹配，尚无全文索引或大规模负载验收。目录 API 的价格排序仍依据主 SKU；Web 的本地价格排序使用有库存规格的最低价格。未修改 Flutter 搜索实现，也未进行线上发布。

## Web / 后台启动

要求 Node.js >= 22.13。所有 Node 命令在本目录执行：

```sh
npm ci
npm run dev:web       # http://localhost:5173
npm run dev:admin     # http://localhost:5174（另一个终端）
npm run typecheck
npm run build:web
npm run build:admin
```

`npm run dev` 与 `npm run build` 仍默认指向 Web，`npm run start` 使用根目录的 Worker 构建输出。`/ops` 保留旧入口，实际后台源码位于 `backend/backend_web/`。原有 `dev:admin` / `build:admin` 命令名保留，执行路径已指向新目录。

本地分别在 `web/.dev.vars`、`backend/backend_web/.dev.vars` 配置 `.env.example` 的变量。若要测试本地模拟登录，店主 ID 使用 `local_seedy`；生产继续使用该站点的真实店主身份 ID。所有 `.dev.vars` 均忽略提交。

两个本地开发服务共享仓库根目录 `.wrangler/state` 的 D1 开发数据。`npm run test:api` 只允许访问本机，会创建一条测试待付款订单，不会支付、发货或访问生产库。

## 商务基础验收（2026-10-10）

```sh
npm run test:commerce # 领域、SQL、服务/HTTP、后台表单及 Web 状态测试；隔离内存库
npm run test:d1       # 实际本地 workerd / D1，非持久化，不读取商家凭证或现有库
npm run test:api      # 本地已启动 Web 的冒烟检查；无可售商品时只检查目录/请求守卫
```

单元与服务测试使用 Node 的 `node:sqlite`（实际验收 Node 24）；本地 D1 测试使用锁文件中的 Miniflare。它们不连接生产、不创建付费交易、不改现有商家库存，也不代表生产负载/安全审计已完成。

商城、结算和后台共用 D1 商品价格及 `max(stock - reserved, 0)` 库存。后台访问不再自动插入演示订单或商品；没有真实数据就显示空列表。商家可新建商品，或显式导入 3 个下架模板；新商品/模板初始库存 0，不覆盖现有 SKU。补齐资料、核实库存并主动上架后，商城才能购买。空库不回退到静态假库存。

订单、商品和入库变更与审计在同一个 D1 batch 中写入，失败一并回滚；商品和订单更新有版本条件保护，避免静默覆盖另一位操作者的改动。后台当前显示最近 200 笔订单、最多 1000 个商品、最近 100 条审计，统计只代表该窗口。

公开目录支持服务端分类、三语言文字检索、价格排序和稳定游标分页，默认每页 50 件、最多 100 件，解除 500 条截断。商品详情按 ID 直接查询；下单只读取已校验购物袋中的商品（最多 20 项），不扫描完整目录。Web/App 当前仍先聚合全部目录再更新购物状态，后页失败不拿半份目录清空购物袋/收藏；Web 总读取限时 15 秒，客户端最多 1000 页。页面每次渲染 24 件，“查看更多”只是展示窗口，不是服务端总数或虚假加载。分页不是固定快照，修改价格/名称可能改变跨页结果；重复 ID/游标时客户端失败关闭。稀疏/非 ASCII 检索可能扫描多批旧行，尚无全文索引、百万级负载验证或按购物袋独立补货状态查询。

Web 丢失下单响应时，进入独立恢复页面，先确认上一次保存结果再允许编辑或提交另一请求；使用原始请求与幂等键，不受后来商品下架或目录加载失败影响。地址/邮箱等资料只在内存，不写入浏览器持久化存储；保存的是请求摘要、键和尝试标志。刷新后若无法重建完全相同请求（例如商品已下架），尚无安全恢复令牌机制，不承诺完整跨刷新恢复。新建不同请求可能生成另一笔待付款草稿，不能把它当原订单的自动恢复。

## Flutter

已使用 Flutter stable 3.47.6 / Dart 3.13.5 创建多平台工程。运行、测试、平台准备见 `app/README.md`。Flutter 与 Web 使用同一个 `/api/v1`，不直接访问数据库，不内置商家秘密。

架构为：界面 → `StoreModel` → `CommerceApi` → 服务端业务 / D1。状态、数据请求与界面分开，遵循 [Flutter 官方架构建议](https://docs.flutter.dev/app-architecture/recommendations)。

## 支付和正式上线边界

支付始终关闭。保存订单是 `pending` / `payment_pending`，不会扣款，不会允许后台推进未付款订单发货。资质齐备后需单独实现支付供应商、验签回调和对账，不能靠改一个开关上线。

本次完成商务基础加固，不代表已达到完整商用验收或亚马逊级规模。下一阶段应依次落实商品批量运营、库存预留与支付后确认、采购/供应商/货代任务和物流回传、售后退款、反滥用与分布式限流、备份/监控/压测与原生端发布。用户管理和认证由其他开发工作负责，除明确要求的代码同步外不扩展；真实收款继续暂缓。税费尚未估算，配送价格是当前配置规则，并非实时承运商报价。

独立用户服务运行方式与环境变量见 `backend/api/README.md`；不会自动装入商城 Worker 或公开部署。隔离用户测试不等于 MySQL/Redis/OAuth 联调成功。历史暴露的 OAuth 凭证需由所有者撤销并轮换；邮件/短信发送、OAuth state/nonce 与账号并发唯一性等仍需负责该模块的开发者完成正式验收。

数据库访问代码与 Drizzle 表结构定义位于 `backend/api/db/`。商务迁移按 `backend/sql/meta/_journal.json` 执行版本化 SQL，商务迁移已登记至 `0006_logistics_integrations.sql`，本次发布新增 `0005_product_variants.sql` 与 `0006_logistics_integrations.sql` 及对应元数据，不改历史迁移。新迁移只追加字段、表、索引，不回填价格、库存或历史订单；历史商品要通过后台主动补齐资料才能进入商城。迁移未应用到生产或现有本地库，部署前应备份并在预发布验收后仅应用未执行项。

`backend/sql/数据库SQL.sql` 是其他开发者新增的用户模块 SQL，不属于 D1/Drizzle 商务迁移，不要把目录所有 `.sql` 混合执行。构建只打包 SQLite journal 明确引用的 SQL 与元数据，排除 MySQL 用户 SQL 和未登记文件。历史订单表的 `payment_status` 物理默认值仍保留，避免贸然重建历史表；本轮所有新订单 INSERT 均显式写入 `pending`。历史缺少请求摘要的旧幂等键不猜测内容匹配，返回 409 要求新的下单尝试。

现有站点托管配置保留。独立服务器发布步骤见 `docs/selfhost-deployment.md`；发布前需备份数据库与媒体，生产构建通过后再切换版本并进行 HTTPS 网页验收。
